# 一页看懂：这个仓库是干什么的

> 本文写给**产品、项目经理及其他非技术同学**。不需要任何编程背景。
> 想直接上手干活的话，去看 [`testing-guide.md`](testing-guide.md)。

## 一句话

DSH 可以装"插件"来扩展能力。这个仓库是插件**交付给用户之前**的两道保护：

- **`conformance`（自动检查）= 安检门** —— 在代码提交时，几秒钟内查出插件"声明与实物不符"的问题。
- **`testkit`（测试工具箱）= 标准模拟舱** —— 让每次自动化测试跑在一间**全新干净**的房间里，从而结果可信、可重复。

一个是**把错误挡在交付之前**，一个是**让测试结论算数**。

## 30 秒版本

插件开发中最贵的事故，都不是"功能写错了"，而是**在最晚的时刻、由最不该发现的人发现**：

| 事故 | 没有这套东西，会在哪里被发现 | 代价 |
|---|---|---|
| 插件声明里写的文件其实不存在 | 用户装完就崩，或联调时才发现 | 用户报障、口碑受损 |
| 插件把 DSH 自带的组件当普通依赖装了一份 | 版本互相遮蔽，功能直接不工作 | 报错难懂，排查极久 |
| 插件声称"支持 1.0 以上所有版本"，其实只测过 1.0 | DSH 升级到 2.0 后某天突然坏 | 无人提前知道，被动救火 |
| 插件用了 DSH 已经删掉的旧接口 | 用户升级 DSH 后失效 | 升级被阻塞 |
| 测试跑在开发者自己的 DSH 环境上 | **永远发现不了** —— 本机能过、别人不能过 | 反复扯皮"我这儿是好的" |
| 测试要调用 AI 模型 | 慢、要花钱、每次结果还不一样 | 无法作为发布依据 |
| **检查配置里路径写错了** | **永远发现不了** —— 一个插件都没查，却显示"通过" | 虚假的安全感，最危险 |

这个仓库就是把这七类问题的发现时刻**尽量往前推** —— 推到提交代码的那几秒钟、推到还没有用户的阶段。

## 全貌：两个包各管一半

| | `packages/conformance`<br>自动检查（安检门） | `packages/testkit`<br>测试工具箱（模拟舱） |
|---|---|---|
| **一句话** | 查插件的**声明与实物是否自洽、与宿主是否兼容** | 给测试一间**一次性、干净、无凭据**的房间，并**真的启动一次**看宿主放不放行 |
| **看不看代码跑起来** | 不跑。纯静态检查 | 真跑。启动真实 DSH |
| **快慢 / 成本** | 秒级、免费、每次提交都能跑 | 较慢；其中模型部分可做到不花钱，运行时探针**也不需要密钥** |
| **抓什么性质的问题** | 交付前的"低级但致命"错误 | "结果不可信 / 不可复现"，以及**"装上了却没生效"**（被宿主静默禁用） |
| **典型使用时机** | 每次提交、每次发版前 | 提交时跑轻量部分；夜间/发版前跑真实启动 |
| **当前规模** | **36 条规则**（5 个规则族） | **45 个用例**（含 10 条真实启动），覆盖隔离、回放、**运行时激活探针** |

两者是**配合**关系，不是替代关系：安检门便宜所以每次都跑，但只能看"箱子里装了什么"；模拟舱贵但必须真跑，才能回答"飞起来稳不稳"。

## 一个比喻：机场登机

把"插件交付给用户"想象成**登机**：

- **安检门**（`conformance`）= 安检机 + 证件核对。它**不负责让你飞**，只负责在登机前把不合规的行李拦下来。
- **模拟舱**（`testkit`）= 给你一间**全新的干净房间**做测试。用过的房间直接拆掉 —— 所以你的测试不会弄脏自己的家（开发者真实的 DSH 环境），也不会被家里原有的东西影响。

# 包一：`conformance` —— 交付前的自动检查

## 它为什么存在

插件出问题，绝大多数不是"逻辑写错了"，而是**声明和实物不一致**：清单里写的文件不存在、导出的入口不一致、依赖的位置放错了、版本号写宽了。这类问题**不需要跑代码就能查出来** —— 只要有一个"对账"的工具，且足够便宜，便宜到每次提交都愿意跑。

## 它能预防和发现的问题

### A. 声明与实物不一致（"说的和带的不一样"）

| 它会发现的问题 | 没有它 → 会在哪爆掉 | 具体怎么拦 |
|---|---|---|
| 清单里**缺包名或版本号** | 插件无法被识别、无法发布，或发布后装不上 | 核对两个必备身份字段是否存在且为文本 |
| 插件清单里声明的补丁文件**不存在** | 加载失败，甚至 DSH 起不来 —— 用户装完就崩 | 把声明的每个文件路径都对着磁盘核一遍 |
| 清单声明了"我是组合包"但**没写补丁文件** | 插件静默失效，什么都不做 | 检查角色声明与配套字段是否成对 |
| 补丁文件列表是**空的** | 同样是静默失效，但表面上"声明过了" | 检出空列表 |
| 清单里某字段**类型写错了**（该是列表写成了字符串等） | 运行时行为诡异或直接崩 | 逐字段核对类型 |
| **对外入口（exports）不完整** —— 少了根入口、少了清单本身，或少了客户端入口 | 用户装好后 import 失败；发布后才发现 | 核对必备入口是否都在 |
| 声明了补丁文件，但它**没有被对外入口覆盖** | 发布后用户拿不到这个文件 → 加载失败 | 交叉核对"补丁文件路径"与"对外暴露的入口" |
| 清单 JSON **语法错误 / 读不出来** | 插件完全无法加载 | 直接报错，并说明是哪个文件 |
| 缺 `engines.dsh`，或版本范围**语法非法** | 宿主兼容性无法表达 / 直接解析失败 | 检查存在性与语法（缺失只提醒，不阻断） |

### B. 组合装载（"插件装进 DSH 时会怎样"）

| 它会发现的问题 | 没有它 → 会在哪爆掉 | 具体怎么拦 |
|---|---|---|
| **把 DSH 自带的核心组件当普通依赖装了一份** | 版本互相遮蔽，**功能直接不工作**，且报错极难懂 | 检出核心包出现在普通依赖里（这条是**错误**级） |
| 同类工具包被重复安装 | 通常无害，但会埋下版本分叉隐患 | 单独列为**提醒**级，不阻断提交 |
| 同一个组件在锁文件里**出现多个版本** | 运行时到底用哪个不确定 → 诡异行为 | 检查锁文件版本唯一性 |
| 组合里出现**重复的装载条目 id** | 后者静默覆盖前者，行为对不上预期 | 检出重复 id，并列出来源 |
| 补丁**引用了没安装的包** | 启动失败 | 逐个引用核对是否真的装了 |
| **组合顺序违反组件自己声明的顺序** | 装载次序错，行为异常且难定位 | 校验顺序与自述是否一致 |
| 补丁**指向已经不存在的条目** | 修改静默失效 | 检出指向空目标的补丁 |

> 这一族的价值在于：它检查的是**插件与宿主拼在一起**之后的样子，而不只是插件自己。很多故障只有组合起来才存在。

### C. 版本与兼容性（"DSH 升级后会不会碎"）

| 它会发现的问题 | 没有它 → 会在哪爆掉 | 具体怎么拦 |
|---|---|---|
| 插件声称支持的版本范围**不包含用户实际在用的 DSH 版本** | 宿主会**拒绝装载**这个插件 → 用户现场失效 | 对着**真实安装的宿主版本**核对，并区分"宿主太旧"与"宿主太新" |
| 插件声称"某大版本以上**全都支持**"（单侧开放的范围） | DSH 升级后突然坏，**且没人提前知道** | 要求把支持的版本线**一条条写清楚**；范围写得过宽就报警，并给出正确写法示例 |
| 声明的兼容范围**自相矛盾**（两处说法不一致） | 行为取决于运行时读哪一处，不确定 | 交叉核对两处声明 |
| 声明"不支持"但**没有走正式的豁免流程** | 要么被静默接受、要么被静默拒绝，没人知道 | 要求显式记录豁免 |
| 豁免**已经过期**（插件版本变了，旧豁免还在） | 豁免悄悄失效或错误地继续生效 | 检查豁免是否仍然对应当前版本 |
| 某类**基础框架依赖**的版本范围不满足宿主（这类依赖**不被宿主预检**） | 不直接报错，但会造成版本遮蔽风险 | 单独列**提醒**级，不与"真正的拒绝"混为一谈 |
| 尚未被用上的"**支撑包**"版本不满足宿主 | 若一律按错误拦下，会误伤还没启用的包 | 区分"已被挂载"与"仅作支撑"，支撑包只**提醒**不阻断 |
| 插件**用了 DSH 已经移除的接口** | 用户升级 DSH 后失效 | 把"DSH 删了什么、从哪个版本起删"做成**数据表**，按宿主版本分级报警 |

**"分级"是什么意思**：同一个缺陷，在旧宿主上是**提醒**（现在还能用，但迁移后会失效），在新宿主上是**错误**（已经坏了）。这样升级风险能提前看到，而不是等用户撞上。

**"数据表"是什么意思**：DSH 每次删接口，只在数据表里**加一行**，检查逻辑不用改代码。所以这个能力会随 DSH 演进而自动增长，不需要每次重新开发。

### D. 专门防"检查本身失效"

这是最容易被忽略、也最要紧的一族 —— 它检查的不是插件，而是**"这次检查到底有没有真的在检查"**：

| 它会发现的问题 | 没有它 → 会在哪爆掉 | 具体怎么拦 |
|---|---|---|
| 配置里写的**路径不存在**（盘符变了、目录改名、复制粘贴写错） | 依赖它的整组检查会**静默跳过**，但结果显示"通过" | 明确报错，并指出是哪个配置项、哪个路径 |
| 配置里的**目标匹配不到任何插件** | 一个插件都没查，却显示"通过" | 报错，并逐个打印没匹配上的模式；**拒绝输出"通过"** |

> 详见下方「最值得一提的一点」。

### 规则族与编号（完整覆盖）

| 规则族 | 编号 | 条数 | 管什么 |
|---|---|---|---|
| 清单与入口 | `DSH-C000` ~ `C044` | 18 | 声明与实物是否一致 |
| 组合装载 | `DSH-C050` ~ `C056` | 7 | 插件装进 DSH 后的组合问题 |
| 版本与兼容 | `DSH-C057`、`C060` ~ `C065`、`C067` | 8 | 与宿主版本是否兼容（含**安装期** semver 维度） |
| 挂载判定 | `DSH-C066` | 1 | 区分"已被挂载"与"仅作支撑"，避免误伤 |
| 门禁自身配置 | `DSH-C070`、`C071` | 2 | 防"空转却显示通过" |
| **合计** | | **36** | |

## 它是怎么被调用的

一条命令跑完全部检查，输出"错误 / 提醒"两种级别：

- **错误**：会真正导致故障 → 必须修，否则检查失败。
- **提醒**：不阻断运行 → 不卡每一次提交，但**发布前要清零**。

退出码也是明确的：`0` 通过、`1` 有错误、`2` 用法错误或**没有检查到任何东西**。

## 它**做不到**什么

- **不启动 DSH**（这是它快的原因，也是它的边界）：所以它**看不到**"装起来之后实际行为对不对"。
- **不评价代码质量**：不看逻辑对不对、性能好不好。
- **不看界面与交互**：好不好用、顺不顺，它一概不管。
- **不保证"没报错就是好的"**：它只保证"它查过的那几类问题不存在"。

这些空白，正是**包二**要补的。

# 包二：`testkit` —— 让测试可信、可重复

## 它为什么存在

团队原本就在做真实的集成测试（真启动 DSH、真装载插件）。机制是对的，但**缺隔离**。没隔离会导致两类问题：

1. **测试结果不可信** —— 受每台机器上原有的配置影响；
2. **测试有副作用** —— 会写脏开发者自己的环境。

而"不可信的测试"比"没有测试"更糟：它会给出错误的信心。

## 它能预防和发现的问题

### A. 测试环境不干净（"结果不可复现"）

| 它会发现/预防的问题 | 没有它 → 会在哪爆掉 | 具体怎么拦 |
|---|---|---|
| 测试跑在**开发者自己的 DSH 环境**上 | 标准配置和你自己的个性化配置都会渗进每一次测试 → **本机能过、别人不能过** | 每次测试发一套**一次性、全新**的环境 |
| 测试**会写入**这个环境 | 已实测：一个只读性质的命令也产生了 2 个文件 —— 测试**不是只读的**，会污染开发者的家 | 用完即删整个环境，副作用归零 |
| 测试继承了你**个人**的配置改动 | 你为了调试做的临时修改会悄悄影响测试结论 | 刻意**不生成**个人配置层 |
| 需要 `npm install` 才能搭出测试环境 | 环境搭建慢、易碎、CI 上成本高 | 已实测**不需要**安装依赖即可启动 —— 组件从 DSH 安装本身解析 |

### B. 测试被"静默放过"（"本该抓到的问题没抓到"）

| 它会发现/预防的问题 | 没有它 → 会在哪爆掉 | 具体怎么拦 |
|---|---|---|
| 真实环境里存在一份**豁免文件**，会**静默授权**本该被拒绝的插件 | 测试用"放行"掩盖了"本该拒绝" → 问题留到**用户现场**才暴露 | 刻意**不生成**豁免文件，让拒绝真实发生 |
| 测试静默继承了开发者的**真实凭据** | 测试结果被环境和额度影响；更糟的是把"需要密钥"这类错误和"插件有问题"混为一谈 | 刻意**不生成**凭据文件；需要密钥时必须**显式**注入 |
| 失败原因指向错误方向 | 明明是环境问题，却被当成代码缺陷，排查跑偏 | 明确区分"进程没起来"（环境问题）与"起来了但失败"（真的结论）两种报告 |

### C. 模型带来的不确定性（"每次跑结果都不一样"）

插件测试常需要调用 AI 模型，这带来三个问题：**慢、花钱、结果不稳定**（模型输出每次都有差异）。工具箱提供两条车道：

| 车道 | 做法 | 用途 | 成本 |
|---|---|---|---|
| **keyless**（默认） | 模型部分放"**录像**"，其它部分真实重跑 | 每次提交的门禁、需要**确定性**的回归 | **零**模型费用 |
| **with-key**（夜间） | 显式注入密钥，接真实模型 | 真实效果验证、统计类评测 | 有费用，故不在每次提交跑 |

关键设计：**"录像"只是模型那一层**，插件自己的工具调用是**真实重跑**的。所以断言验证的仍然是真实世界，不是一段假的录像。

### D. 测试资产的可维护性

| 它会发现/预防的问题 | 没有它 → 会在哪爆掉 | 具体怎么拦 |
|---|---|---|
| 被测插件**没有被真正装进**测试环境 | 测试跑的是旧版本，"通过"毫无意义 | 按绝对路径把被测插件链进测试环境 |
| 测试产物**写错位置** | 例如豁免文件没放对地方 → 测试静默失效 | 明确约定各文件的落点 |

### E. 插件**被宿主悄悄禁用**（"装上了，但根本没生效"）

这是最阴险的一类失败：插件代码没问题、也能装进环境，但宿主在启动时判定它**与当前 DSH 版本不兼容**，于是**把它整行关掉**。用户看到的现象是"这个插件怎么没反应"，而日志里那一行禁用说明早就滚过去了。

| 它会发现/预防的问题 | 没有它 → 会在哪爆掉 | 具体怎么拦 |
|---|---|---|
| 插件**被宿主静默禁用**（版本不兼容） | 用户现场"插件不生效"，而开发者本地因为有一份**豁免文件**从没复现过 | **真实启动一次**，断言启动日志里没有"禁用该行"的记录 |
| 插件**启动失败**（不是被禁用，而是起不来） | 报错被淹没在启动日志里，或干脆表现为"功能缺失" | 一并捕获"未激活""在等待服务""加载树失败"三类启动故障 |
| 检查工具**自己**是坏的（要么查不出、要么永远报错） | "检查通过"变成一句空话 —— 比不检查更糟 | 用**两个只差一个版本范围**的对照插件做受控实验，**自证能查出**，也**自证不是永远失败** |

**为什么这条车道不能省**：只做静态检查（读文件）会**恰好漏掉这一类** —— 实测证明，把配置"打印出来看"时，一个不兼容的插件会**原样出现在配置里，既没有被标记禁用、也没有任何提示**。禁用决定只在**真实启动**的那一刻做出。所以"配置看着没问题"**不等于**"插件真的能用"。

**成本**：一次真实启动（秒级），**不需要密钥、不需要外部客户端、不需要联网调模型** —— 因为禁用决定发生在调用模型**之前**。

## 它**做不到**什么

- **不判断插件逻辑对不对**：它提供可信的环境，**结论要你自己写断言**。
- **不替代人工测试**：界面、交互、体验完全不在范围内。
- **不覆盖外部依赖**：外部引擎、客户端桥这类"活体"验证属于人工范畴。
- **不做安装期验证（但已建模其中一类）**：**运行时探针**只回答"宿主放不放行这一行"，不会真的去 `npm install`，所以它不回答"装的时候会不会被拒绝"。**静态门禁**已经把这一维里最有价值的一类建模进来了 —— `DSH-C067` 会指出"范围只被运行时接受、会被安装期的裸 semver 拒绝"（典型成因：宿主是预发布版本，范围缺少同元组预发布比较器）。真正的完整安装过程仍属包管理器，不在本仓库范围内。
- **测试支撑包（`dsh-llm-replay` / `dsh-session-snapshot`）与 DSH 同步发版，且把自己的 peer 钉成精确版本**：所以拿一条宿主线的支撑包去跑**另一条**宿主线时，宿主自己的预检会禁用它，replay 车道随之不可用。工具箱会**优先取宿主里的那一份**，取不到就带着两边版本号明确跳过（而不是抛一句难懂的 `NO_ADAPTER`）。要用 replay 车道跑某条宿主线，需按该宿主版本把这两个包装进宿主 `node_modules`。

# 两者怎么配合

```
开发者改完插件
      │
      ├─ 提交代码 ──► 【安检门】秒级静态检查 ──► 不合格：当场拦下（几秒钟内，还没有用户）
      │                    │
      │                    └─ 合格 ──► 【模拟舱·运行时探针】真实启动一次 ──► 宿主禁用了某行？此时发现
      │                                        │
      │                                        └─ 放行 ──► 【模拟舱·回放测试】行为回归 ──► 行为不对？仍在自己手里
      │
      └─ 发布 ──► 用户安装 ──► 若都没拦住，问题在这里爆发（最贵）
```

一句话记住分工：

- **安检门**回答：**"这个插件看起来装得上去吗？"**（便宜、每次都问）
- **模拟舱**回答：**"它真的装上去之后，宿主放行了吗、行为对吗？"**（较贵、但必须真问）

三层里最容易被漏掉的是**中间那一层**：静态检查说"声明没问题"，回放测试说"行为没问题"，但**宿主在启动时把插件整行关掉**这件事，只有"真实启动一次并看启动日志"才能发现 —— 而它恰恰表现为"插件毫无反应"这种最难排查的现场故障。

# 最值得一提的一点：**"没查"绝不等于"通过"**

这是整套设计里最容易被忽略、也最要紧的一条。

早期的版本有个隐患：如果配置里的路径写错了（比如盘符变了、目录改名了、复制粘贴写错了），检查程序会**一个插件都没查到** —— 但因为它"没有发现任何问题"，就报告**通过**。

> 这比漏掉某一条具体规则危险得多：它给的是**虚假的安全感**。团队以为有保障，实际上什么都没查。

现在的行为是：这种"空转"会被明确判为**失败**，程序会把"哪个路径没匹配到东西"逐条打印出来，并且**拒绝输出"通过"**。

同理，**跳过也从不伪装成通过**：如果环境缺少真实 DSH 安装，相关用例会明确标记为"跳过"并写出原因（是哪个配置、哪个路径缺），既不显示成通过，也不显示成失败。

# 它**不**做什么（整体边界）

- **不替代人工测试**：不评价界面好不好用、交互顺不顺、体验如何。
- **不做模型效果评测**：模型答得好不好属于另一条统计车道，**不卡发布**。
- **安检门不启动 DSH、不联网、不写磁盘**：所以它快、便宜、可以挂在每一次提交上。
- **它不是 DSH 插件本身**：它是装在**开发者这一侧**的独立工具，不会进入用户的 DSH。

# 现在的状态（如实说明）

- 两个工具包目前都是**私有**的（标了 `private`）、用的是**占位包名**，**尚未发布**到任何仓库。
  对外发布前还需要两件事：确定正式包名，以及**确定许可证** —— 许可证目前**尚未决定**，因此两个包里都**没有**填写许可证字段（而不是先随便写一个）。
- 已接入自动流程：每次提交自动跑 **174 个**单元用例（自动检查 129 + 工具箱 45），其中 11 个在接上真实宿主后真正执行。
- 其中 **10 个**用例需要"真实安装的 DSH"才能跑（9 个真实启动 + 1 个宿主接口面核对）。在没有该安装的环境（例如 CI）里，它们会**自动跳过**，并写明**是哪个变量、哪个路径**缺失。完整要求见 [`ci-real-host.md`](ci-real-host.md)。
- 这套东西刚经过一轮系统复核，修掉了若干问题，包括"路径写错却显示通过"和几类**误报**（误报的危害是大家会开始绕过门禁）。每条修复都补了**回归用例**。

# 常见问题

**Q：插件已经在用了，还需要过这道门禁吗？**
需要，但价值体现在**变更时**。已经装好的插件不会因为它而变坏；下次改它、或 DSH 升级时，它就是拦住回归的那道闸门。

**Q：两个包是不是重复了？只用一个行不行？**
不重复，各回答一个不同的问题（见上方"两者怎么配合"）。只用安检门，你永远不知道"真装上去行为对不对"；只用工具箱，你会把大量低级错误留到真跑那一步，既慢又晚。

**Q：会不会很慢，拖累开发进度？**
安检门不启动 DSH、不联网，是**秒级**的，可以挂在每次提交上。工具箱里较慢的是"真实启动"和"接真实模型"那两层，只在需要时才跑。

**Q：会不会误报，导致大家干脆绕过它？**
这正是它被反复打磨的地方 —— 误报比漏报更能摧毁一个门禁的可信度。最近一轮修复就专门处理了几类误报，并逐条补了回归用例。同时问题分两级：会真正导致故障的算"错误"必须修；不阻断运行的算"提醒"，不卡每次提交但发布前清零。

**Q：这套东西是谁在维护？**
规则依据记在 [`contract-v1.md`](contract-v1.md)（团队契约 v1），变更走测试负责人维护的修订台账并通知全体。落地前还剩几项待办（正式包名、仓库地址、CI 上的真实 DSH 安装），清单在根目录 [`README.md`](../README.md) 的"落地待办"一节。
